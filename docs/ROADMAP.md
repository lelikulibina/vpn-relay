# Roadmap рефакторинга vpn-relay

Целевая ветка: `refactor/modular-control-api-nftables`

Документ фиксирует этапы рефакторинга и критерии завершения. Изменения поведения сетевого datapath не должны смешиваться с механическим переносом кода.

## Принципы

- Сохранять публичную совместимость там, где она заявлена проектом.
- Делать изменения небольшими, проверяемыми и обратимыми.
- Не удалять старую реализацию до проверки эквивалентности новой.
- Сетевые интеграционные тесты должны быть изолированы друг от друга и не зависеть от порядка запуска.
- CI должен давать быстрый feedback: короткие проверки запускаются часто, длительные независимые группы — параллельно в отдельных GitHub Actions jobs.
- Не сохранять тест только ради покрытия строк: каждый тест должен защищать важный контракт, сценарий отказа или регрессионный риск.

## R1 — Модульная архитектура

Цель: декомпозировать крупные модули без изменения сетевой семантики.

- Разделить ответственность `runtime.rs`, `linux.rs`, `config.rs`, `routing.rs` на предметные модули.
- Выделить границы между control plane, runtime, Linux backend, routing и конфигурацией.
- Устранить циклические зависимости и скрытые побочные эффекты инициализации.
- Сохранить публичный API и существующие конфигурационные форматы.
- Переносить код небольшими сериями с тестами до/после.

Критерии готовности:
- структура модулей отражает ответственность, а не только размер файлов;
- публичные контракты и конфигурация не изменились без отдельного решения;
- форматирование, clippy, unit и необходимые интеграционные проверки проходят.

## R2 — Control API и управление демоном

Цель: отделить команды управления и наблюдаемость от механизма работы демона.

- Ввести транспортно-независимую модель команд/ответов.
- Использовать Unix socket как основной локальный транспорт; не связывать доменную логику с Unix socket.
- Предусмотреть совместимость старого и нового протокола на период миграции, если это требуется существующими клиентами.
- Вывод статистики выполнять по запросу клиента, а не непрерывным потоком в stdout.
- Разделить запуск, остановку, запрос состояния и получение статистики.
- Не делать systemd обязательным: предусмотреть работу с systemd, OpenRC (включая Alpine) и ручным запуском/супервизором.

Критерии готовности:
- команды управления имеют документированный и тестируемый контракт;
- ошибки транспорта не смешаны с ошибками бизнес-логики;
- демон может работать в фоне без постоянного вывода статистики в stdout;
- проверены сценарии запуска, остановки, повторного подключения и аварийного завершения.

## R3 — Типизированная реализация nftables

Цель: перейти к типизированному построению правил через Rust-крейт `nftables`.

- Инвентаризировать все места генерации и применения nftables ruleset.
- Сформировать типизированную внутреннюю модель таблиц, цепочек, правил, выражений и объектов.
- Перевести генерацию на API крейта без изменения семантики правил.
- Сравнивать нормализованный результат старой и новой реализаций на репрезентативных конфигурациях.
- Проверить apply, readback, идемпотентность, обновление и rollback.
- После доказанной эквивалентности удалить старый текстовый генератор, строковые подстановки и дублирующий парсинг.

Критерии готовности:
- все production-пути формирования ruleset используют типизированную реализацию;
- старый генератор удалён, а не оставлен как скрытый fallback;
- есть тесты семантики правил и интеграционные проверки в network namespace;
- проверены IPv4/IPv6, NAT, forwarding, policy routing и сценарии очистки — в той мере, в какой они поддерживаются проектом.

## R4 — Ревизия тестовой системы и ускорение CI

Цель: оставить минимальный, но достаточный набор тестов и выполнять независимые длительные проверки параллельно.

### R4.1 — Полный аудит существующих тестов

Составить реестр тестов: Rust unit/integration tests, shell-тесты, network namespace сценарии, тесты протоколов, multi-uplink и Podman.

Для каждого теста зафиксировать:
- какой контракт или риск он проверяет;
- уровень проверки: unit, component, integration, end-to-end;
- время выполнения и необходимые привилегии/зависимости;
- детерминированность, изоляцию ресурсов и возможность параллельного запуска;
- пересечение с другими тестами и уникальную ценность.

По результатам принять явное решение: оставить, объединить, переписать, перенести на nightly/manual либо удалить. Удалять тест только после подтверждения, что его уникальный сценарий покрыт другим тестом или больше не является поддерживаемым контрактом.

### R4.2 — Минимально достаточная тестовая пирамида

- Unit-тесты: быстрые, без root и внешней сети; проверяют чистую логику, преобразования, валидацию и обработку ошибок.
- Component-тесты: проверяют взаимодействие внутренних модулей и системные адаптеры с контролируемыми зависимостями.
- Network integration: только реальные kernel/network namespace сценарии, которые нельзя надёжно проверить на более низком уровне.
- End-to-end/deployment: ограниченный набор критичных сценариев запуска и работы в контейнере/системе.
- Не дублировать один и тот же сценарий на нескольких уровнях без конкретной причины.

### R4.3 — Параллельные протокольные тесты

Сценарии сетевого трафика для каждого поддерживаемого протокола должны выполняться независимо и параллельно в отдельных GitHub Actions jobs:

- WireGuard (WG);
- AmneziaWG 3 (AWG 3);
- AmneziaWG 3.1 (AWG 3.1).

Для каждого варианта — отдельный job/элемент matrix с собственным окружением, логами и timeout. Общая сборка может переиспользоваться через artifact/cache, но тестовые namespace, интерфейсы, адреса, процессы и временные файлы не должны пересекаться.

Перед включением параллелизма:
- устранить фиксированные имена ресурсов и глобальное состояние;
- обеспечить уникальные имена namespace/temp paths на job и на тест;
- гарантировать cleanup через trap/finally даже при ошибке;
- проверить повторный запуск и конкурентный запуск;
- не запускать несколько rootful сетевых сценариев на одном runner, если они меняют общие host-level ресурсы.

### R4.4 — Разделение GitHub Actions

Разнести длительные независимые группы по отдельным jobs (а при необходимости — отдельным workflow), чтобы GitHub Actions выполнял их одновременно:

- `quality`: fmt, check, clippy и быстрые unit-тесты;
- `kernel-compatibility`: проверки поддерживаемых версий Ubuntu/kernel;
- `network-core`: базовые routing/firewall/NAT сценарии;
- `protocol-wg`: WG peer traffic;
- `protocol-awg3`: AWG 3 peer traffic;
- `protocol-awg31`: AWG 3.1 peer traffic;
- `multi-uplink`: отдельная проверка multi-uplink;
- `podman`: deployment smoke/integration.

Фактическое число jobs определить по длительности и ресурсной конкуренции после аудита. Не дробить короткие тесты искусственно, если накладные расходы runner и повторная сборка делают CI медленнее.

Настройки:
- `fail-fast: false` для независимой matrix, чтобы получить результаты всех протоколов;
- явные `timeout-minutes` для каждой долгой группы;
- кеширование Cargo и, где оправдано, передача собранного бинарника как artifact;
- отдельные читаемые имена jobs и сохранение логов при падении;
- PR workflow должен запускать обязательный быстрый набор и все критичные сетевые проверки;
- редкие/дорогие дополнительные сценарии могут выполняться по расписанию или вручную, если это не ослабляет проверку критичных контрактов.

### R4.5 — Критерии готовности тестовой системы

- Каждый оставшийся тест имеет объяснимую уникальную ценность.
- Нет случайных зависимостей между тестами и порядка их выполнения.
- WG, AWG 3 и AWG 3.1 выполняются параллельно в независимых jobs.
- Длительные независимые группы не блокируют друг друга последовательным запуском в одном job.
- Повторные и конкурентные запуски стабильны.
- В CI видны длительность, логи и причина падения каждой группы.
- Удалённые тесты перечислены в аудите с причиной удаления и ссылкой на покрывающий тест/изменение контракта.

## R5 — Совместимость и выпуск

- Проверить поддерживаемые версии Linux и kernel.
- Проверить сценарии без systemd, включая Alpine/OpenRC.
- Проверить установку, обновление, запуск, остановку и восстановление после ошибки.
- Проверить конфигурационную и control-протокольную совместимость.
- Обновить документацию, примеры конфигурации и release notes.

## Рекомендуемая последовательность

1. Зафиксировать baseline и провести аудит текущих тестов (R4.1) до массового рефакторинга.
2. Выполнить R1 с сохранением существующего поведения.
3. Выполнить R2 и проверить lifecycle/control-контракты.
4. Выполнить R3 с доказательством эквивалентности nftables ruleset.
5. Реализовать новую структуру CI и параллельные протокольные jobs (R4.2–R4.5); часть безопасных CI-улучшений можно делать раньше, сразу после аудита.
6. Завершить матрицу совместимости и выпуск (R5).

Порядок допускает раннее выполнение аудита тестов и CI-инфраструктуры: это не требует ждать завершения модульного рефакторинга. При этом удаление тестов и изменение их семантики должны сопровождаться отдельным обоснованием.
