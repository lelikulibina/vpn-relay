# Черновой план Web UI

> Статус: предварительный черновик. Документ фиксирует согласованное направление, а не окончательное техническое задание. Детали будут уточняться после сверки с текущей архитектурой и возможностями Rust daemon.

## 1. Цель и принципы

Создать простую и удобную web-панель для одного администратора `vpn-relay`. Это не многопользовательская корпоративная система управления.

Основные принципы:

- Не переусложнять интерфейс и архитектуру.
- Сохранить Rust daemon единственным backend и местом реализации бизнес-логики.
- Не вводить отдельный Python- или Node.js backend.
- Не предоставлять браузеру root-доступ, произвольное выполнение команд или прямое управление системными инструментами.
- Сначала использовать уже имеющиеся возможности daemon; новые механизмы добавлять по мере необходимости.
- Все операции изменения состояния должны проходить через типизированный API и проверки daemon.

## 2. Предполагаемая архитектура

### Frontend

- Vue 3 с Composition API.
- TypeScript.
- Последняя стабильная версия Tailwind CSS на момент начала реализации.
- Vite для сборки.
- UI собирается отдельно и поставляется вместе с приложением; Rust daemon раздаёт собранные статические файлы.

### Backend

- HTTP API встроен непосредственно в существующий Rust daemon.
- Версионирование API, например префикс `/api/v1/`.
- Для обновления логов и статистики в реальном времени рассмотреть WebSocket или Server-Sent Events (SSE).
- Выбор HTTP-фреймворка и конкретной схемы интеграции отложить до изучения текущей структуры daemon.
- Системные операции, валидация конфигурации и управление WG/AWG остаются в Rust.

## 3. Авторизация и безопасность

Панель рассчитана на одну административную учётную запись:

- Без регистрации, приглашений, ролей и управления несколькими пользователями.
- Настройка административного пароля при первоначальной настройке.
- Хранение хеша пароля с использованием Argon2id.
- Защита от перебора пароля.
- Безопасные сессии, явный выход, смена пароля и тайм-аут неактивности.
- Защита API от CSRF и других типичных web-атак.
- При внешнем доступе — HTTPS непосредственно или через reverse proxy.
- Не возвращать приватные ключи и другие секреты в API без строгой необходимости; не записывать их в логи.

Безопасный сценарий первоначальной установки и восстановления доступа нужно отдельно спроектировать.

## 4. Основные разделы интерфейса

### 4.1 Dashboard

Краткая сводка:

- Состояние daemon.
- Количество активных VPN-интерфейсов.
- Общее количество пиров и число недавно активных пиров.
- Общий объём переданного/полученного трафика и текущая скорость.
- Состояние основных сетевых компонентов.
- Последние важные события и ошибки.

Главная страница не должна быть перегружена: подробная информация находится в соответствующих разделах.

### 4.2 VPN-интерфейсы

Список интерфейсов с основной информацией:

- Имя и тип (WireGuard или AmneziaWG).
- Состояние.
- Адрес и порт.
- Количество пиров.
- RX/TX.

Страница интерфейса:

- Подробная конфигурация.
- Список пиров.
- График трафика и статистика.
- Связанные ошибки и события.

Предусмотреть действия start, stop, restart и edit. Создание, удаление и изменение интерфейсов включать с учётом фактических возможностей и ограничений daemon. Перед удалением показывать, какие пиры, маршруты и другие ресурсы будут затронуты.

### 4.3 Пиры

Список пиров с фильтрацией по интерфейсу. Отображаемые поля:

- Имя и публичный ключ.
- Интерфейс.
- AllowedIPs и endpoint.
- Время последнего handshake.
- RX/TX и скорость.
- Расчётный статус активности.

Предусмотреть создание, редактирование, удаление и временное отключение пира, генерацию клиентской конфигурации, QR-кода и скачивание конфигурации. По возможности автоматически подбирать свободный IP из подсети интерфейса.

WireGuard не предоставляет универсального достоверного признака «онлайн». Статус активности следует рассчитывать по handshake и/или сетевой активности с понятными порогами; эти пороги должны быть определены отдельно.

### 4.4 Конфигурация

- Просмотр текущего TOML.
- Визуальный редактор основных параметров.
- Расширенный редактор TOML.
- Проверка конфигурации до применения.
- Предварительный просмотр diff.
- Резервная копия перед применением.
- Применение конфигурации и отображение результата или ошибок.

### 4.5 Импорт WG/AWG

- Импорт одного или нескольких файлов стандартных конфигураций WireGuard и AmneziaWG (`.conf`).
- Предварительный просмотр распознанных параметров.
- Проверка совместимости с возможностями vpn-relay.
- Выбор целевого интерфейса и параметров импорта.
- Явный отчёт о неподдерживаемых или неоднозначных параметрах.

Нельзя молча отбрасывать неизвестные или неподдерживаемые параметры: пользователь должен видеть, что именно не будет импортировано и почему.

### 4.6 Статистика

- Трафик по интерфейсам и отдельным пирам.
- RX/TX speed.
- Общая статистика и топ пиров по объёму трафика.
- Периоды: час, сутки, неделя и месяц.
- История должна собираться daemon независимо от того, открыт ли браузер.

Для хранения истории нужна периодическая агрегация счётчиков. Не следует сохранять каждое изменение счётчика как отдельную запись. Формат, частоту сбора и механизм хранения определить после оценки нагрузки и существующих зависимостей проекта.

### 4.7 Логи и события

- Уровни debug, info, warn и error.
- Фильтрация по интерфейсу и уровню.
- Поиск.
- Обновление в реальном времени.
- Просмотр подробностей и экспорт.

Помимо системных логов, полезно показывать события управления: изменение конфигурации, создание/удаление пира, запуск и остановку интерфейса.

Приватные ключи, пароли, токены и другие секреты никогда не должны попадать в логи.

### 4.8 Состояние системы

Диагностическая страница для просмотра:

- Состояния vpn-relay.
- nftables.
- IPv4 forwarding.
- Сетевых интерфейсов.
- Маршрутов и ip rules.
- Uplink.
- Ошибок системных операций.

На первом этапе раздел преимущественно read-only. Изменение системных правил должно выполняться через штатную конфигурацию и механизмы daemon, а не произвольным редактированием из UI.

### 4.9 Резервные копии

Предусмотреть создание, скачивание, загрузку, проверку целостности и восстановление резервных копий. Если копии содержат секреты, необходимо продумать их шифрование и безопасное обращение с ключами.

## 5. Что не входит в первоначальный объём

Пока не планируются:

- Несколько пользователей, роли, регистрация и приглашения.
- Уведомления через Telegram или email.
- Сложная аналитика.
- Отдельный backend на Python или Node.js.
- Web terminal и произвольное выполнение команд.
- Автоматическое обновление операционной системы.
- Плагинная система UI.

К этим возможностям можно вернуться отдельно, если появится реальная необходимость.

## 6. Предварительные этапы реализации

| Этап | Содержание |
|---|---|
| P0 | Встроенный API, авторизация, раздача статических файлов UI |
| P1 | Dashboard, список и просмотр интерфейсов, список и просмотр пиров |
| P2 | Управление интерфейсами и пирами |
| P3 | Просмотр/редактирование конфигурации и импорт WG/AWG |
| P4 | Статистика и долговременная история трафика |
| P5 | Логи, диагностика системы и резервные копии |

Порядок предварительный и может измениться после технического аудита.

## 7. Что необходимо уточнить перед реализацией

1. Какие операции управления интерфейсами и пирами уже доступны внутри Rust daemon и какие можно безопасно переиспользовать.
2. Какие runtime-метрики и системные состояния daemon уже умеет получать.
3. Как устроены текущие конфигурация, reload, import и обработка ошибок.
4. Как встроить HTTP-сервер и раздачу UI, не нарушив текущую архитектуру и lifecycle daemon.
5. Нужны ли WebSocket или достаточно SSE для обновлений.
6. Как хранить историю статистики с минимальным числом новых зависимостей.
7. Как безопасно реализовать первичную настройку пароля, сессии и восстановление доступа.
8. Какие операции UI должны быть доступны в первой версии, а какие следует отложить.

## 8. Ограничения текущего проекта, которые UI должен учитывать

На момент составления черновика проект ориентирован на Linux и поддерживает IPv4. Он управляет WireGuard/AmneziaWG TUN-интерфейсами, peer lifecycle, policy routing, nftables, NAT и forwarding. В проекте уже заявлены runtime reload конфигурации и отдельная операция замены набора пиров.

Web UI не должен предполагать поддержку IPv6, неподдерживаемых платформ или системных операций, которых нет в daemon. Все перечисленные функции необходимо сверить с реализацией до проектирования API.
